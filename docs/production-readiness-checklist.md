# Twilite production readiness checklist

Пункты расположены не по тематическим разделам, а по зависимостям: следующий этап не должен начинаться, пока не готов фундамент предыдущего.

Статусы отмечены по состоянию репозитория на 8 августа 2026 года. Отмечены только пункты, которые подтверждаются кодом, конфигурацией или CI. Наличие модуля без доказанного рабочего сценария не считается выполнением.

> Юридический раздел не является юридическим заключением. Перед коммерческим запуском документы и модель обработки данных нужно проверить с юристом по юрисдикциям, где будет доступно приложение.

## Этап 0. Зафиксировать MVP и модель данных

Без этого бессмысленно полировать интерфейс, писать юридические документы и подключать оплату.

- [ ] Зафиксирован основной сценарий: `регистрация → создание пространства → приглашение партнёра → добавление момента → синхронизация → возвращение через неделю`.
- [x] Зафиксировано, что такое хороший момент, сложный момент, поверхность, история и архив.
- [x] Определены роли, права и видимость: только я, оба партнёра, администратор пространства.
- [x] Определены состояния объекта: активный, тускнеющий, архивный, удалённый.
- [ ] Определены лимиты: длина текста, размер аудио/изображений, частота AI-запросов, количество пространств.
- [ ] Определены данные, которые собираются: email, IP, device/push ID, тексты, аудио, аналитика, платежи, AI-история.
- [ ] Определены сроки хранения и правила удаления каждого типа данных.
- [ ] Определено, будет ли Twilite работать с несовершеннолетними и пользователями за пределами РФ.

## Этап 1. Довести основной пользовательский путь до рабочего состояния

Это первый настоящий приоритет. Пока пользователь не может пройти цикл от регистрации до совместного момента, остальные фичи не имеют ценности.

- [ ] Онбординг объясняет идею Twilite за 30 секунд.
- [ ] Регистрация, вход, выход и восстановление доступа работают полностью.
- [ ] Пользователь может создать пространство пары.
- [ ] Можно пригласить партнёра по ссылке или коду.
- [ ] Есть состояния «партнёр ещё не подключился», «приглашение принято» и «приглашение истекло».
- [ ] Пользователь может добавить хороший момент и сложный момент.
- [ ] У записи есть текст, автор, дата, время и тип.
- [ ] Реализованы просмотр, редактирование и удаление собственной записи.
- [ ] Работают главная поверхность, детальный просмотр и история.
- [ ] Во всех экранах есть loading, empty, error и retry-состояния.
- [ ] Основной путь работает на реальных iOS и Android устройствах.

## Этап 2. Подготовить production-инфраструктуру и базовую безопасность

Сначала защищаем фундамент, затем на него навешиваем синхронизацию, приватность и платежи.

- [ ] Есть отдельные dev, staging и production окружения.
- [ ] Production использует HTTPS и защищённый WebSocket.
- [ ] Все секреты хранятся в Secret Manager, а не в репозитории.
- [ ] Приложение падает при старте с дефолтными JWT-секретами.
- [ ] Access/refresh токены имеют короткий TTL, refresh-токены ротируются и отзываются.
- [ ] Выход, смена пароля и удаление аккаунта инвалидируют активные сессии.
- [ ] Есть rate limit для входа, регистрации, восстановления пароля, AI и WebSocket.
- [x] Права проверяются на backend для каждого пространства и объекта.
- [ ] CORS ограничен production-доменами, Redis и Postgres закрыты от интернета.
- [ ] Валидация ограничивает размер, тип и содержание пользовательских файлов и текста.
- [ ] Медиа защищены приватными URL с ограниченным сроком действия.
- [ ] В логах нет токенов, паролей, текстов записей, AI-промптов и платёжных данных.
- [ ] Есть базовая защита от abuse: блокировка, лимиты, жалоба и техническая модерация.

## Этап 3. Сделать данные и синхронизацию надёжными

Realtime нельзя считать готовым, пока нет источника истины, восстановления после потери соединения и понятного поведения при конфликте.

- [x] HTTP остаётся источником истины, а WebSocket только доставляет изменения.
- [ ] Realtime работает между двумя устройствами одного пространства.
- [ ] При потере WebSocket клиент автоматически переподключается.
- [ ] Пропущенные события восстанавливаются через HTTP.
- [x] Есть offline-очередь, повторная отправка и понятный индикатор синхронизации.
- [ ] Конфликт optimistic locking показывает пользователю корректное состояние и не теряет запись.
- [x] Миграции выполняются автоматически в CI/CD и имеют план отката.
- [ ] Postgres backup настроен, а восстановление из backup проверено.
- [x] Healthcheck проверяет API, Postgres, Redis, очереди и хранилище.
- [ ] Реализован graceful shutdown для HTTP, WebSocket, Redis, очередей и БД.

## Этап 4. Закрыть приватность и обязательные пользовательские действия

Документы должны описывать уже реализованное поведение, поэтому этот этап идёт после определения данных и базовой архитектуры.

- [ ] В приложении есть политика конфиденциальности и пользовательское соглашение.
- [ ] Есть отдельное согласие на обработку персональных данных.
- [ ] Пользователь может запросить экспорт своих данных.
- [ ] Пользователь может удалить аккаунт прямо в приложении.
- [ ] Удаление очищает аккаунт, пространства, записи, медиа, AI-историю и токены, кроме данных, которые нужно хранить по закону.
- [ ] Есть публичная web-страница для запроса удаления аккаунта.
- [ ] Есть публичная страница поддержки и контакт оператора данных.
- [ ] В политике описаны email, IP, device/push ID, аудио, тексты, аналитика, платежи, AI и сроки хранения.
- [ ] Отдельно описано, передаются ли данные Sentry, PostHog, AI-провайдеру, хостингу и платёжным сервисам.
- [ ] Реализованы отзыв согласия, исправление данных и обращение пользователя.
- [ ] Проверен возрастной порог и исключён сбор данных детей без отдельного compliance-процесса.
- [ ] Проверена необходимость уведомления Роскомнадзора об обработке персональных данных.
- [ ] Проверено первичное хранение персональных данных граждан РФ в базах данных на территории РФ, если это применимо.
- [ ] Проверена трансграничная передача данных для AI, Sentry, PostHog, хостинга и магазинов приложений.
- [ ] Подготовлены внутренние регламенты доступа, уничтожения данных и реагирования на инциденты.

## Этап 5. Настроить тестирование, наблюдаемость и релизы

Нельзя выпускать приватные и платёжные функции без автоматической проверки критичных сценариев и возможности отката.

- [x] CI запускает frontend/backend typecheck, lint, unit и integration tests.
- [ ] E2E покрывает регистрацию, приглашение, создание записи, права, удаление и восстановление подключения.
- [ ] Production-сборка воспроизводима через CI/CD.
- [ ] Настроены Sentry, uptime-monitoring и алерты на 5xx, latency, падение очередей и ошибки webhook.
- [ ] Составлен runbook: rollback, восстановление БД, ротация секретов и реакция на инцидент.
- [ ] Все зависимости проверяются на уязвимости, lock-файлы коммитятся.
- [ ] Проверены Privacy Manifest и требования сторонних SDK.
- [ ] Проверены background/foreground, плохая сеть, обновление, переустановка и малый объём памяти.
- [ ] Проверены accessibility: VoiceOver, TalkBack, Dynamic Type, контраст и touch-зоны.

## Этап 6. Завершить MVP перед публичной beta

После этого уже есть смысл приглашать реальных пользователей, а не просто показывать прототип.

- [ ] Есть поиск и фильтры истории: период, автор, тип и состояние.
- [ ] Есть настройки уведомлений и возможность полностью отключить push.
- [ ] Есть профиль, настройки приватности, смена email и пароля.
- [ ] Есть поддержка и отправка обращения.
- [ ] Есть настройка видимости записи: только я, оба партнёра или временная запись.
- [ ] Deep links работают для приглашений и восстановления доступа.
- [ ] Состояние приложения корректно восстанавливается после background, обновления и переустановки.
- [ ] Настроены русский и английский языки либо зафиксирован подтверждённый язык MVP.
- [ ] Аналитика отслеживает activation, retention, создание первой записи, приглашение партнёра и возвращение в приложение без отправки содержимого записей.
- [ ] Реализован сценарий жалобы и блокировки контента.
- [ ] Проведён закрытый тест на реальных парах и исправлены блокирующие проблемы.

## Этап 7. AI, аудио и чувствительный контент

Подключать это после базового сценария и приватности. Иначе получится дорогой и юридически рискованный слой поверх недоказанного продукта.

- [ ] AI имеет лимиты по частоте, длине и бюджету.
- [ ] Пользователь явно понимает, какие данные отправляются AI-провайдеру.
- [ ] AI не использует персональные тексты для обучения без отдельного согласия.
- [ ] Есть политика хранения и удаления AI-истории.
- [ ] AI-дисклеймер говорит, что это не врач, психолог и сервис экстренной помощи.
- [ ] Для контента о самоповреждении, насилии и кризисе есть безопасный fallback с экстренными ресурсами.
- [ ] Аудио имеет ограничения размера, формат, срок хранения и удаление.
- [ ] В аналитике и логах не сохраняются тексты и аудиосодержимое.

## Этап 8. Платежи и публикация в магазинах

Платежи идут после того, как понятна ценность продукта и есть рабочий privacy-контур.

- [ ] Для подписки есть Terms, Privacy, Restore Purchases и понятные цены.
- [ ] RevenueCat webhook проверяет подпись, идемпотентность и повторную доставку.
- [ ] Статус подписки подтверждается backend, а не доверенным клиентом.
- [ ] Проверены отмена, возврат, истечение, grace period и восстановление покупки.
- [ ] Проверена применимость оферты, налогов, чеков и 54-ФЗ для выбранной модели продаж.
- [ ] Заполнены Apple App Privacy и Google Play Data Safety на основе фактического поведения SDK.
- [ ] Privacy Policy URL добавлен в App Store Connect и Google Play.
- [ ] В Google Play указана web-страница удаления аккаунта.
- [ ] Для iOS и Android подготовлены возрастной рейтинг, описание, скриншоты и review-инструкция.
- [ ] Подготовлен тестовый аккаунт для модерации.
- [ ] Проверено, что цифровые функции не оплачиваются через запрещённый внешний эквайринг внутри приложения.

## Этап 9. После подтверждения retention и спроса

- [ ] Мягкие ежедневные или еженедельные ритуалы.
- [ ] Реакции партнёра без токсичной соревновательной механики.
- [ ] Комментарии к моментам.
- [ ] Дайджест недели и визуализация изменений поверхности.
- [ ] Экспорт поверхности как изображения или PDF.
- [ ] Темы оформления и dark mode.
- [ ] Подсказки для разговора и AI-рефлексия по накопленным моментам.
- [ ] Расширенная история, платные темы и дополнительные пространства.
- [ ] Виджеты, календарь и wearables.
- [ ] Web-версия для экспорта, поддержки и удаления аккаунта.
- [ ] A/B-тестирование онбординга и paywall.
- [ ] Админ-панель: пользователи, abuse, подписки, webhook-повторы, retention и conversion.
- [ ] Реферальная программа.

## Definition of Ready for public launch

Twilite можно выпускать публично только если выполнены этапы 0–8, нет известных критичных security/privacy-дыр, удаление аккаунта реально проверено на staging, платежи протестированы в sandbox, а основной сценарий проходит E2E на iOS и Android:

`регистрация → создание пространства → приглашение партнёра → добавление момента → синхронизация → возвращение через неделю → удаление аккаунта`.

Главный совет: не расширять AI, подписку и социальные механики, пока этот цикл не работает стабильно. Красивый 3D-слой не спасёт продукт, если партнёр не может подключиться или пользователь не может удалить свои данные.
