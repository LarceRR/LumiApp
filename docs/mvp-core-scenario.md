# Основной сценарий MVP

Источник требования: `docs/production-readiness-checklist.md`, Этап 0 → «Зафиксирован основной сценарий».

Это единственный сквозной сценарий, по которому проверяется готовность MVP. Пока он не проходит целиком, остальные фичи (AI, подписка, социальные механики) не считаются ценностью и не берутся в работу.

| | |
| --- | --- |
| Версия документа | 1 |
| Автоматизация | `backend/test/integration/mvpCoreScenario.spec.ts` |
| Последний прогон на staging | не проводился (см. «Журнал прогонов») |

Сценарий: `регистрация → создание пространства → приглашение партнёра → добавление момента → синхронизация → возвращение через неделю`.

## Роли

- **A (Аня)** — регистрируется первой, создаёт общее пространство, приглашает партнёра. Роль в пространстве: `Owner`.
- **B (Борис)** — принимает приглашение и ставит момент на поверхность. Роль: `Member`.

Парный принцип домена: в общем пространстве объект ставит **партнёр**, а не автор события. Поэтому момент про A создаёт B (`subjectUserId` по умолчанию = второй участник).

## Предусловия

1. Развёрнуто окружение staging: API, Postgres, Redis; миграции применены; `GET /health` отвечает `200` со `checks.database = up` и `checks.cache = up`.
2. Известны базовый URL API и версия сборки клиента (записываются в журнал прогонов).
3. Аккаунтов A и B не существует: почты свободны.
4. Два независимых клиента: два устройства (iOS + Android) для ручного прогона либо два HTTP-клиента для прогона по API.
5. Ручных обходов не используется: никаких правок в БД, ручных подтверждений приглашений и подмены состояний.

## Шаги и ожидаемые результаты

| № | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | A регистрируется: `POST /v1/auth/sign-up` | `201`. Выданы access/refresh токены. Личное пространство создано той же операцией: `GET /v1/spaces` возвращает ровно одно пространство типа `Personal`. |
| 2 | B регистрируется тем же способом | `201`, своё личное пространство. |
| 3 | A создаёт общее пространство: `POST /v1/spaces` | `201`, `type = Shared`, один участник — A с ролью `Owner`, `version = 1`. |
| 4 | A приглашает B по почте: `POST /v1/spaces/{spaceId}/invitations` | `201`, приглашение в статусе `Pending`, адресовано почте B. |
| 5 | B видит приглашение: `GET /v1/spaces/invitations/pending` | `200`, ровно одно приглашение с названием пространства. Состояние «партнёр ещё не подключился» видно у A. |
| 6 | B принимает: `POST /v1/spaces/invitations/{invitationId}/respond` | `201`, статус `Accepted`. В пространстве два участника. У B в `GET /v1/spaces` появляется общее пространство. |
| 7 | B добавляет момент: `POST /v1/spaces/{spaceId}/surface-objects` с `kind = Fire` и заметкой | `201`, `state = Emerging`, `version = 1`, `createdByUserId = B`, `subjectUserId = A`. Координаты выбрал сервер: клиент их не передаёт. |
| 8 | Клиент B завершает появление: `POST /v1/surface-objects/{objectId}/state` с `transition = activate` и `version = 1` | `201`, `state = Active`, `version = 2`. |
| 9 | A синхронизируется: `GET /v1/spaces/{spaceId}/surface`, `GET /v1/spaces/{spaceId}/timeline`, `GET /v1/spaces/{spaceId}/timeline/statistics` | `200`. Поверхность содержит один объект в состоянии `Active` с тем же `version`. История содержит `MemberJoined`, `SurfaceObjectCreated`, `SurfaceObjectStateChanged`. Статистика: `totalObjects = 1`, `byKind.Fire = 1`. |
| 10 | «Возвращение через неделю»: B входит заново на другом устройстве (`POST /v1/auth/sign-in`), запрашивает поверхность, обновляет пару токенов (`POST /v1/auth/refresh`) | `200`. Поверхность и история те же: состояние сохранилось между сессиями и устройствами. Refresh выдаёт новую пару токенов. |

## Ожидаемый результат сценария

Сценарий считается пройденным, если одновременно верно всё:

- Обе регистрации, создание пространства, приглашение, принятие, создание момента и смена состояния прошли без ручных обходов.
- Второй участник видит момент партнёра, историю и статистику без переустановки приложения и без ручного сброса кеша.
- После повторного входа состояние поверхности и истории идентично тому, что было до выхода.
- Ни одна повторная отправка мутации не создала дубликат сущности (таблица ниже).
- Все запросы отдали ожидаемые коды; ошибок `5xx` в логах за время прогона нет.

## Идемпотентность повторной отправки и источник истины

Правило: **backend — источник истины**. HTTP-ответ определяет состояние, WebSocket только доставляет изменения, клиент всегда отправляет `version`, которую видел, и после конфликта перечитывает состояние, а не «дожимает» свою версию. Offline-очередь клиента повторяет действие только при сетевой ошибке, а конфликт (`409`) снимает действие с очереди и ре-синхронизирует поверхность.

| Мутация | Повторная отправка | Результат |
| --- | --- | --- |
| `POST /v1/auth/sign-up` с той же почтой | `409` | Второй аккаунт не создаётся. |
| `POST /v1/spaces/{id}/invitations`, приглашение ещё `Pending` | `409` | Второе приглашение не создаётся: частичный уникальный индекс по `(space_id, invitee_email) where status = 'Pending'`. |
| `POST /v1/spaces/{id}/invitations` после принятия | `422` | Приглашать участника пространства нельзя. |
| `POST /v1/spaces/invitations/{id}/respond` повторно | `409` | Статус меняется только из `Pending`. Участник не дублируется: членство пишется upsert-ом по `(space_id, user_id)`. |
| `POST /v1/surface-objects/{id}/state` с устаревшей `version` | `409` | Состояние на сервере не меняется, клиент обязан перечитать объект. |
| `PATCH /v1/surface-objects/{id}` с устаревшей `version` | `409` | То же: optimistic locking, запись не теряется. |
| `DELETE /v1/surface-objects/{id}?version=` с устаревшей `version` | `409` | Удаление по устаревшей версии не выполняется. |
| `POST /v1/spaces/{id}/surface-objects` повторно | `201` **и второй объект** | ⚠️ Пробел: у создания нет ключа идемпотентности. См. «Известные пробелы». |

## Автоматизация

Сценарий покрыт сквозным smoke-тестом по API: `backend/test/integration/mvpCoreScenario.spec.ts`.

```bash
cd backend
npm run db:migrate
RUN_INTEGRATION=1 npm test
```

Тест поднимает реальный граф приложения (Nest + Fastify + Postgres + Redis) и ходит по маршрутам через `app.inject`, поэтому падает на пропавшем маршруте, сломанном контракте, потерянном праве и на регрессе идемпотентности. В CI выполняется в job «Бэкенд» на шаге с `RUN_INTEGRATION=1`.

Что **не** покрыто автотестом и проверяется руками до релиза:

- realtime-доставка между двумя устройствами и восстановление пропущенных событий после разрыва WebSocket;
- прогон на реальных iOS и Android (UI-состояния loading/empty/error/retry, deep links приглашения);
- реальное старение объекта за неделю (`Fading` → `Settled` планировщиком).

## Известные пробелы

1. **Нет ключа идемпотентности у создания момента.** Offline-очередь повторяет действие при сетевой ошибке, а потерянный ответ на успешный `POST` неотличим от несостоявшегося запроса → у пары появляется дубликат момента. Нужен `clientRequestId` (или заголовок `Idempotency-Key`) с уникальным индексом и возвратом ранее созданного объекта.
2. **Повторное принятие приглашения инкрементит `version` пространства перед отказом:** участник добавляется до смены статуса приглашения, поэтому второй `respond` успевает поднять версию и только потом получает `409`. Порядок операций стоит перевернуть.
3. **Прогон на staging не выполнен:** отдельного staging-окружения ещё нет (Этап 2 чеклиста). До этого пункт Этапа 0 остаётся незакрытым.
4. **E2E на устройствах не настроен:** Detox есть в зависимостях, конфигурации и сценария нет.
